# 内存不足对策

会出现 “ビットマップ用メモリを確保できません/……” 或 “Cannot allocate memory for Bitmap : ……” 之类的错误。  
似乎由于画面的大型化等原因，这种错误变得越来越容易发生。  
吉里吉里Z 与 2 相比更不容易发生，但并非不会发生。  
不过，可以通过设置来减少发生。  

## 原因
游戏中出现这种错误时，比起内存真的不足，更多是由内存碎片化引起的。  
图像等需要较大区域的内存分配与小型类、字符串等内存分配混在一起时，容易发生内存碎片化。  
内存碎片化加剧后就无法分配大块内存，在尝试分配位图用内存等较大区域时便会失败。

## 对策
根据内存管理算法的种类，其中也有不易产生碎片化的算法，采用这种算法也是一种办法；Windows Vista 以后采用了不易产生碎片化的算法，碎片化似乎已有所减轻。  
即使在 XP 上，通过启用 [LFH](https://msdn.microsoft.com/ja-jp/library/windows/desktop/aa366750%28v=vs.85%29.aspx) 也能获得同样的效果(吉里吉里Z 面向 Vista 以后，因此始终有效)。  
不过，即使此功能有效，有时仍会发生，因此还有其他对策，例如执行压缩整理（compaction）、分离图像用内存区域等。

### 压缩整理
所谓压缩整理，是指将内存中相邻的空闲区域连接起来，形成大块连续的空闲区域。  
在多次进行内存分配/释放的情况下会有一定程度的负载升高，因此偶尔执行即可。  
在吉里吉里Z 中，通过添加 -ghcompact 选项(可在引擎设置中指定)，会在 System.doCompact 被调用时对全局堆执行压缩整理。  
由于是稍微有些负载的处理，因此默认为禁用。  
如果在目标的最低规格 CPU 上启用后也能无压力运行，那么将其默认启用后发布也没有问题。

### 分离堆
将只分配较大区域的位图用内存与其他内存分离，从而防止碎片化加剧。  
可以通过引擎设置进行指定。  
默认从进程堆进行分配，多数情况下这样没有问题。  
如果测试中会出现（该错误），就试着启用；如果能够减轻，最好将分离堆设为默认设置。

### 调用 GC
在脚本中，于场景切换的黑场等时机调用 System.doCompact，似乎会有一些效果。

### 不使用图形缓存
图形缓存不使用，或者尽量减小其容量，对抑制内存碎片化更有效。  
如果采取上述对策后仍没有效果，则也有余地去考虑不使用图形缓存。  
不使用图形缓存时，尤其在快进时会明显感觉变重，但在配备近年 CPU 与 SSD 的环境中并没有那么令人介意，因此直接不使用缓存也没有问题。

### 使用 64bit 版
如果上述对策全部实施后仍没有效果，最好考虑使用作为终极对策的 64bit 版。  
可以充分利用已安装的内存，也能消除“明明装了大量内存却仍会发生”的不满。  
如今在任何环境下 64bit 都逐渐成为理所当然，因此无论是否与内存不足有关，今后最好都准备好 64bit 版。
