# 吉里吉里Z 特有的防破解对策
吉里吉里2/Z 由于其高度的扩展性，在试图破解时存在多个会成为切入点的部位。  
这里记述吉里吉里特有的对策。

## 可执行文件替换对策
在进行认证的情况下，如果可以被替换成没有任何检查的可执行文件来运行，那就等同于没有采取任何对策。  
需要做到与可获取到的可执行文件替换后无法运行。  
还要注意替换为通过补丁或体验版发布等公开的可执行文件后仍能运行的情况。  
要使目标游戏数据、DLL 等只有在特定的可执行文件下才能运行。  
只要内置了加密 xp3 的解密处理，其他可执行文件就无法启动。  
不过，如果解密后的归档被制作出来就会失去意义，所以最好再追加一些其他特有的功能。  
为了使过去被破解的可执行文件无法使用，需要持续进行开发。

## 自动加载插件的抑制
存在自动加载扩展名为 tpm 的 dll 的功能，但如果被自动加载，就可能实现内置 API 的替换等，因此必须使其无法做到。  
不过，采取这一对策后，将无法使用利用内置功能的插件进行的加密。

## 自动加载脚本的抑制
由于 data.xp3 内的 startup.tjs 等初期加载的脚本是固定的，如果它被替换，就可能实现内置 API 的替换等，因此必须使其无法做到。  
通过将初期读取的脚本位置固定为一处、进行脚本的篡改检测、对 xp3 进行加密并在每次读取时解密，可以在一定程度上避免特定脚本以外的插入。  
通过在编译时将任意字符串设置到 TVP\_START\_UP\_SCRIPT\_NAME 来在启动时执行任意脚本，并抑制通过 -startup 选项执行任意脚本。  
也可以通过 TVPSystemSecurityOptions 指定强制从 data.xp3 读取等。

## 插件替换对策
通过重命名原插件并放置同名的插件，就可以加载任意插件，从而可以劫持该插件公开的 API，或替换内置 API。  
如果替换 krmovie.dll 等负责文件读取的 dll，就能轻易获取传递给该 dll 的数据(1.3 以后 krmovie.dll 被内置到本体中，因此就 krmovie.dll 而言这一问题不复存在)。  
就 krmovie.dll 而言是视频文件，KAGParser.dll 系则是 KAG 脚本。  
为回避这一问题，需要检测 dll 的篡改。  
例如查看要加载的 dll 的哈希、进行电子签名检查。  
不过，检查耗时会影响运行，因此需要能够进行高速检查。  
如果干脆将插件内置到本体中，使插件本身无法使用，就不必在意这些了。  
虽然通过 [Extension](http://www.kaede-software.com/2014/01/extension.html) 功能可以添加功能，但目前无法在不变更插件源代码的情况下进行。  
目标是：在不更改源代码的情况下，通过更改构建方式制作静态库，并将其与本体链接，从而实现内置到本体中。

## 抑制通过热键唤出的控制器、脚本编辑器、监视表达式、控制台
在吉里吉里Z 中，“控制器、脚本编辑器、监视表达式”已被删除，控制台则变为命令行。  
[删除的功能](../tjs2/deleted.md)  
禁用这些功能。  
在吉里吉里Z 中，通过插件也能获得控制台输出，因此也要抑制这一点。  
禁用控制台输出本身，估计会稍稍加快速度。
在不带 TVP\_LOG\_TO\_COMMANDLINE\_CONSOLE 的情况下构建，日志就不会输出到命令行(公开二进制为 ON，会输出)。  
如果要禁用控制台输出，由于也存在将 OSS 许可证输出到日志的类型的插件，使用这类插件时，需要另行随附写有 license 的文本，因此需要注意。

## 字节码化
如果 TJS2 脚本以原样的状态保存，解析会变得容易，因此将脚本字节码化。  
字节码化可以通过 Scripts.compileStorage 进行。  
即使归档已加密，也总有被突破的可能，因此让脚本难以解析是有意义的。  
另外，字节码比脚本读取得更快(因为脚本的编译已事先完成)。

## 字节码的混淆
为了使字节码难以解析而进行混淆。  
混淆主要通过替换可读的字符串，使处理难以被推测。  
如果能同时混淆内置函数，则会更为强力。  
目前尚未提供 TJS2 字节码的混淆工具等。

## 归档的加密
xp3 归档可以通过向 Releaser 提供加密 dll 来加密。  
解密则通过加载 tpm 插件来进行。
